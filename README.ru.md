**Omega-Fuzz** — локальное терминальное приложение (TUI [Textual] + скриптуемый CLI), выполняющее обнаружение веб-ресурсов и проверки веб-безопасности (HTTP-фаззинг) в авторизованных средах (лаборатории, личные зеркала и явно согласованные тестовые работы).

Это шестой инструмент набора `omega-` (после `omega-scan`, `omega-stress`, `omega-check`, `omega-deep` и `omega-fold`), построенный по принципам Clean Architecture. Полные технические сведения приведены в `docs/ARCHITECTURE.md`.

## 1. Назначение и область

### Что делает Omega-Fuzz

- Обнаруживает область одной цели с помощью BFS, ограниченного явным scope (схема/поддомены/разрешённые и заблокированные пути/глубина), всегда с защитными ограничениями.
- Выполняет общий фаззинг параметров query string, HTTP-заголовков и форм `GET`, найденных на каждой обнаруженной URL, и проверяет три семейства сигнатур: неразрушающий отражённый XSS, общую инъекцию (обнаружение ошибок в ответе), а также отсутствующие или неправильно настроенные заголовки безопасности. См. [§5](#5-выполняемые-проверки-безопасности).
- Оценивает каждую аномалию по трём осям (влияние/эксплуатируемость/охват) и выводит уровень серьёзности (`low`/`medium`/`high`/`critical`), удаляя дубликаты по `(type, endpoint, parameter)` и сохраняя лучшее доказательство. См. [§6](#6-оценка-и-серьёзность).
- Поддерживает аутентификацию (cookie, bearer token, форму входа) через отдельный YAML-файл; учётные данные никогда не передаются в командной строке.
- Показывает результаты в TUI (Textual) или через скриптуемый CLI, поддерживая три формата экспорта (JSON, Markdown и HTML с 5 темами).
- Хранит постоянную историю сканирований и их findings (SQLite), а также повторно используемый список избранных целей.
- Требует явного подтверждения (строгой фразы для наиболее чувствительных случаев) перед агрессивным или расширенным сканированием, а также перед сканированием с отключённой проверкой TLS.

### Чего Omega-Fuzz не делает

- Фаззинг JSON-тел: код существует (`plugins/fuzzers/json_body_fuzzer.py`), но не подключён (HTML/BFS-обнаружение не создаёт схему JSON API и не предоставляет пригодный источник шаблонов).
- Фаззинг форм `POST`/`PUT`/`DELETE`: намеренно исключён из автоматического pipeline из-за риска нежелательных записей на цели; тестируются только формы `GET`.
- Проверки бизнес-логики (IDOR, контроль авторизации, нарушения workflow): код существует (`plugins/logic_tests/`), но остаётся вне автоматического pipeline и может запускаться только отдельно; стандартное сканирование его никогда не запускает.
- Параллельное сканирование нескольких целей: одна цель за одно сканирование.
- Повторный запуск, сравнение или экспорт из экрана История: сохраняются только `Scan` и `Finding` (не полная фактическая конфигурация и не запросы); повторный запуск или экспорт из истории создавал бы недостоверные данные, поэтому экран объясняет ограничение, а не предлагает такую возможность молча.
- Клиентский рендеринг JavaScript (страница загружается в том виде, в котором отдана сервером, но не выполняется в headless-браузере).
- Веб-панель управления.

## 2. Установка

### Требования

- Python 3.10+
- Подключение к Интернету для установки зависимостей
- Для TUI: установленный в терминале [Nerd Font](https://www.nerdfonts.com/) для значка заголовка. Без неё символ отображается пустым квадратом (такое же ограничение, как у emoji, хотя Nerd Font гораздо шире доступен пользователям терминала). Отсутствие шрифта не влияет на работу и имеет только косметическое значение.

### Установка

```bash
[ -d omega-fuzz ] && echo "ℹ️ Уже распаковано здесь, шаг пропущен." || tar -xzf omega-fuzz.tar.gz
cd omega-fuzz/
chmod +x install.sh
./install.sh
```

`install.sh`:

1. Создаёт виртуальное окружение `.venv`, если оно ещё не существует.
2. Устанавливает зависимости (`vendor/omega-lib/`, затем `pip install -e .`; `pyproject.toml` остаётся единственным источником истины).
3. Делает `omega-fuzz.sh` и `install.sh` исполняемыми.
4. Добавляет alias `fuzz` в `~/.bashrc` и `~/.zshrc` (без дублирования, если он уже существует).

### Зависимости

Указаны в `pyproject.toml` (`requirements.txt` отсутствует):
- `omega-lib`: общая библиотека набора (темы экспорта, обнаружение терминала, `ConfidenceLevel`) — включена в `vendor/omega-lib/`
- `httpx`: асинхронные HTTP-запросы (обнаружение + фаззинг), потоковая обработка ответа (полный ответ никогда не буферизуется в памяти, даже если цель отдаёт файл размером в несколько ГБ)
- `beautifulsoup4` + `lxml`: извлечение URL и HTML-форм
- `jinja2`: шаблонизация HTML-экспорта
- `textual`: интерфейс TUI, темы и автоматическая адаптация к терминалу
- `pyyaml`: загрузка файла `--auth-config`
- Зависимости разработки (`pip install -e ".[dev]"`): `pytest`, `pytest-asyncio`, `pytest-cov`, `pytest-httpserver`, `ruff`, `mypy`, `import-linter`

## 3. Использование

### Интерактивный режим (TUI)

Рекомендуется для ежедневного использования — запускается без аргументов:

```bash
./omega-fuzz.sh
```
Если alias создан, просто введите в терминале:
```bash
fuzz
```

Сценарий: стартовый экран (закрывается после нажатия клавиши или щелчка) → главное меню (Scanner / Targets / Settings / History / Help) → ввод цели (полный URL, обязательна схема `http://`/`https://`), preset или ручная конфигурация (scope + aggressiveness), дополнительная аутентификация, проверка TLS, переопределение лимитов → экран проверки (простое подтверждение или строгая фраза `OUI-J-AI-L-AUTORISATION` для чувствительных случаев) → сканирование (индикатор неопределённого прогресса, кнопка **Остановить** доступна в любой момент) → результаты (findings, экспорт) → история (подробности прошлого сканирования и связанные findings) и избранные цели из главного меню. Адаптация к терминалу (цвета, размер, структурное упрощение) выполняется автоматически.

#### Сочетания клавиш

| Клавиша | Действие |
|---|---|
| `↑` / `↓` | Переход между элементами экрана |
| `Tab` / `Shift+Tab` | Переход между полями формы |
| `Esc` | Возврат на предыдущий экран (на домашнем экране запрашивается подтверждение выхода) |
| `t` | Следующая тема (применяется сразу, без подтверждения) |
| `r` | Обновить обнаружение терминала |
| `a` | Показать справку (включая таблицу preset) |
| `q` | Выйти (с подтверждением) |
| `Ctrl+P` | Палитра команд (Theme, Quit, Screenshot) |

### Скриптуемый режим (CLI)

```bash
# Сканирование с готовым preset
./omega-fuzz.sh scan --target https://example.com --preset prod-safe

# Ручная комбинация scope + aggressiveness (без preset)
./omega-fuzz.sh scan --target https://example.com --scope-profile standard --aggressiveness standard

# С аутентификацией (YAML-файл; никогда не передавайте учётные данные в командной строке)
./omega-fuzz.sh scan --target https://example.com --preset staging-full --auth-config auth.yaml

# Dry run: фактическая конфигурация и расчётный план; запросы не отправляются
./omega-fuzz.sh scan --target https://example.com --preset prod-safe --dry-run

# Выборочный экспорт (каталог, форматы, тема HTML)
./omega-fuzz.sh scan --target https://example.com --preset prod-safe \
    --output-dir ./rapports --format html --export-theme omega-neon
```

Параметры `scan`:

| Параметр | По умолчанию | Действие |
|---|---|---|
| `--target` | *(обязательно)* | URL цели; схема `http://`/`https://` обязательна (автоматически не дополняется) |
| `--preset` | — | Готовый preset (см. [§4](#4-профили-scope-и-preset)) |
| `--scope-profile` | — | Профиль scope, комбинируемый с `--aggressiveness`, без `--preset` |
| `--aggressiveness` | — | Уровень агрессивности, комбинируемый с `--scope-profile`, без `--preset` |
| `--auth-config` | — | YAML-файл аутентификации |
| `--insecure-tls` | отключён | Отключает проверку TLS (требует усиленного подтверждения) |
| `--max-duration` | *(из профиля)* | Переопределяет максимальную длительность (секунды) |
| `--max-requests` | *(из профиля)* | Переопределяет максимальное количество запросов |
| `--max-tests` | *(из профиля)* | Переопределяет максимальное количество тестов |
| `--max-concurrent` | *(из профиля)* | Переопределяет максимальную степень параллелизма |
| `--dry-run` | отключён | Показывает фактическую конфигурацию и расчётный план; запросы не отправляются |
| `--output-dir` | `var/exports/` | Каталог экспортированных отчётов с именами `<preset>-<timestamp>.<ext>` (можно изменить в Settings) |
| `--format` | `all` | `json`, `markdown`, `html` или `all` |
| `--export-theme` | `omega-base` | Тема экспортируемого HTML-отчёта (не влияет на json/markdown) |

В CLI нет подкоманды `history`/`show`: историю и избранные цели можно просматривать только из TUI.

Если alias создан через `install.sh`, команда `fuzz scan ...` работает из любого места в терминале без префикса `./omega-fuzz.sh`.

## 4. Профили scope и preset

### Профили scope

| Профиль | Режим | Макс. глубина | Ограничения |
|---|---|---|---|
| `strict` | точная цель | 1 | Блокирует `/health`, `/ready`, `/metrics`, `/favicon.ico`, `/robots.txt` |
| `standard` | + поддомены | 2 | Блокирует распространённые статические поддомены, технические пути и ресурсы (images/css/js/fonts) |
| `large` | + поддомены | 4 | Блокирует только технические пути и ресурсы (включая архивы/PDF) |
| `api` | точная цель | 3 | Ограничен `/api`, `/v1`, `/v2`; блокирует документацию и ресурсы |
| `custom` | + поддомены | 3 | По умолчанию ограничений нет — основа для ручной конфигурации |

Независимо от выбранного профиля список бинарных или крупных расширений (`.iso`, `.zip`, `.exe`, `.mp4`...) **всегда** исключается из обхода и фаззинга, даже в `custom`. Ссылка на такой файл никогда не загружается реальным HTTP-запросом, чтобы каталог загрузок не замедлял сканирование на многие минуты.

### Уровни агрессивности

`doux` · `standard` · `agressif` · `violent` — каждый уровень имеет собственные базовые ограничения (длительность, запросы, тесты, глубина и параллелизм), которые при необходимости переопределяются preset.

### Готовые preset

| Preset | Scope | Aggressiveness | Макс. длительность | Макс. запросов | Макс. тестов | Макс. глубина | Усиленное подтверждение |
|---|---|---|---|---|---|---|---|
| `prod-safe` | strict | doux | 300 с | 1 000 | 500 | 1 | нет |
| `staging-full` | standard | standard | 1 800 с | 20 000 | 10 000 | 2 | нет |
| `lab-deep` | large | agressif | 3 600 с | 100 000 | 50 000 | 4 | нет |
| `lab-extreme` | large | violent | 7 200 с | 500 000 | 250 000 | 5 | **да** |
| `api-hardened` | api | agressif | 1 800 с | 50 000 | 25 000 | 3 | нет |

Сканирование заблокировано, пока пользователь не подтвердит его запуск. **Усиленное** подтверждение (необходимо ввести точную фразу `OUI-J-AI-L-AUTORISATION`) требуется при наличии хотя бы одного из трёх факторов: агрессивность `violent`, preset `lab-extreme` или отключённая проверка TLS (`--insecure-tls`). При отсутствии этих факторов необычная комбинация требует обычного подтверждения «да/нет».

## 5. Выполняемые проверки безопасности

Автоматический pipeline выполняется для каждой URL, обнаруженной в scope, и каждой найденной там формы `GET`:

| Проверка | Условие запуска | Что проверяется |
|---|---|---|
| Общий фаззинг параметров | Каждый параметр query string | Поведение цели при граничных или некорректных значениях |
| Фаззинг заголовков | Один раз для каждой URL, 4 фиксированных заголовка (`User-Agent`, `Referer`, `X-Forwarded-For`, `Accept-Language`) | Поведение цели при граничных или некорректных значениях заголовка |
| Фаззинг формы (только `GET`) | Каждое поле найденной в scope формы `GET` | Поведение цели при граничных или некорректных значениях поля формы |
| Отражённый XSS | Каждый параметр query string | Нефильтрованное отражение payload в ответе (неразрушающий тест) |
| Общая инъекция | Каждый параметр query string | Обнаружение ошибки сервера в ответ на payload инъекции (без специфического SQL/NoSQL fingerprinting) |
| Заголовки безопасности | Один раз для каждой URL | Отсутствующие или неправильно настроенные заголовки безопасности в ответе |

Первые три проверки (общий фаззинг параметров/заголовков/форм) являются движком мутаций **без обнаружения**: они никогда напрямую не создают `Finding`; учитываются только обнаруженные ошибки сервера (5xx) в соответствующем `Test`. Findings создаются только сигнатурами (XSS, инъекция и заголовки безопасности).

## 6. Оценка и серьёзность

Каждая обнаруженная аномалия оценивается по трём осям (`impact`, `exploitability`, `scope`, каждая от 1 до 5) в зависимости от характера наблюдения. Сопоставление намеренно **консервативное** (нижняя часть диапазона, без человеческого подтверждения на этом автоматическом этапе):

| Итоговый балл (сумма 3 осей) | Серьёзность |
|---|---|
| ≥ 13 | `critical` |
| ≥ 10 | `high` |
| ≥ 7 | `medium` |
| < 7 | `low` |

Ручная корректировка (`severity_override`) возможна, но всегда требует явного обоснования. Эквивалентные findings (одинаковые тип, endpoint и параметр) удаляются как дубликаты с сохранением лучшего доступного доказательства (сначала уровень уверенности `omega_lib.core.confidence.ConfidenceLevel`, затем итоговый балл при равенстве).

## 7. Аутентификация

Отдельный YAML-файл (`--auth-config`); учётные данные никогда не передаются в командной строке:

| Режим | Действие |
|---|---|
| `none` | Без аутентификации (по умолчанию) |
| `cookie` | Cookie сессии, передаваемая напрямую |
| `bearer_token` | Токен `Authorization: Bearer ...` |
| `login_form` | Аутентификация через форму (URL входа, поля пользователя и пароля) |

## 8. Архитектура

Omega-Fuzz построен по **Clean Architecture** (domain / application / infrastructure / interfaces / ports / core / app / plugins), соответствует шаблону набора `omega-` (см. `omega-check`/`omega-deep`/`omega-fold`) и проверяется с помощью `import-linter` после каждого изменения. Полное описание находится в **`docs/ARCHITECTURE.md`**.

Краткий обзор:

```text
src/omega_fuzz/
├── domain/          Чистая бизнес-логика (цели/scope, запросы, тесты, findings, профили, отчёты...)
├── application/     Сценарии использования (commands/queries) и оркестраторы (обнаружение, сканирование, отчёт, лимиты)
├── ports/           Контракты приложения (http_client, repositories, exporters...)
├── infrastructure/  Конкретные реализации (httpx, BeautifulSoup, SQLite, экспортёры Jinja2 — Textual находится НЕ здесь)
├── interfaces/      tui/ (Textual) и cli/ (скриптуемый), со строгим функциональным соответствием
├── plugins/         Fuzzers и сигнатуры (чистые функции, без прямого доступа к сети)
├── app/             Сборка (Container, composition root, жизненный цикл)
└── core/            Общая терминология, ошибки и константы
```

Правила проектирования:
- `plugins/fuzzers/` и `plugins/signatures/`: чистые функции, создающие планы тестов (`Test` + `ScanRequest`); они никогда не обращаются к `HttpClient`.
- `infrastructure/network/`: выполняет сетевые операции (`httpx`, потоковая обработка с ограничением памяти); никогда не выносит суждения.
- `infrastructure/analyzers/`: читает уже полученный ответ и создаёт структурированные объекты `Observation`; никогда не пересчитывает оценку.
- `interfaces/`: только отображает данные и не содержит бизнес-логики.

## 9. Экспорт

По умолчанию отчёты создаются в `var/exports/` (runtime-путь привязан к каталогу проекта; для переопределения используется `$OMEGA_FUZZ_VAR_DIR`, также путь можно изменить в Settings) либо по пути, указанному через `--output-dir`. Имя плоское, без подкаталогов: `<preset>-<timestamp>.<ext>` (например, `prod-safe-2026-09-01_14-30-22.html`).

### JSON, источник истины

Полная структура отчёта (фактическая конфигурация, статистика, тесты и findings), строго сериализуемая в JSON.

### Markdown, компактный отчёт для чтения

Читается вне терминала и не содержит ANSI-кодов.

### HTML, автономный веб-отчёт

Доступно 5 тем (`--export-theme` в CLI, селектор в TUI): `omega-base`, `omega-burn`, `omega-neon`, `light-basic`, `light-alt`.

## 10. История и избранные цели

Каждое сканирование сохраняется (SQLite, `var/db/omega-fuzz.db`) вместе с findings и доступно на экране История в TUI. Хранятся только `Scan` и `Finding`, без фактической конфигурации и подробных запросов, поэтому повторный запуск, сравнение и новый экспорт с этого экрана невозможны (экран объясняет это вместо создания недостоверных данных).

На экране **Targets** хранится список избранного (нормализованные URL, `var/targets.json`), который можно использовать для непосредственного заполнения поля Target при новом сканировании.

## 11. Снимки экрана

Команда **Screenshot** в палитре (`Ctrl+P`) по умолчанию сохраняет SVG текущего экрана TUI в `var/screenshots/`. Путь можно изменить в Settings, как и каталог экспорта. В Settings доступна отдельная очистка.

## 12. Совместимость с терминалами

TUI (Textual) автоматически определяет возможности терминала (эмулятор и размер) и соответствующим образом адаптирует структурную таблицу стилей (`complete`/`standard`/`reduced`/`mono`) без ручного флага. Режим CLI всегда остаётся обычным текстом и не зависит от терминала. Политика общая для всего набора `omega-` (`omega-lib`, `terminal/policies.py`).

### Профиль по обнаруженному эмулятору

| Эмулятор | Начальный профиль |
|---|---|
| Ghostty, Alacritty, WezTerm, Kitty | `complete` |
| Konsole, GNOME Terminal, Terminator, Xfce4 Terminal | `standard` |
| xterm, urxvt, современный SSH | `reduced` |
| Linux TTY, устаревший SSH | `mono` |
| Неизвестный эмулятор | `reduced` (резервный профиль по умолчанию) |

### Профиль по размеру терминала

| Минимальный размер (столбцы × строки) | Верхняя граница профиля |
|---|---|
| 120 × 32 | `complete` |
| 100 × 28 | `standard` |
| 80 × 24 | `reduced` |
| меньше | `mono` |

Итоговый профиль — **наиболее ограничительный из двух** (эмулятора и размера); его можно обновить в реальном времени клавишей `r`.

## 13. Тесты

```bash
source .venv/bin/activate
lint-imports        # проверяет Dependency Rule (6 контрактов)
pytest -q           # 317 тестов
ruff check src tests
mypy -p omega_fuzz
```

Структура: `tests/unit/` (domain и application, без реального I/O), `tests/integration/` (реальная файловая система через `tmp_path`, фиктивный HTTP-сервер `pytest-httpserver`, настоящая база SQLite, CLI от начала до конца), `tests/tui/` (навигация через `Pilot`, структурные проверки; автоматическая визуальная проверка не заявляется).

## 14. Вне области

- Фаззинг JSON-тел (код присутствует, но не подключён — обнаружение схемы API отсутствует)
- Фаззинг форм `POST`/`PUT`/`DELETE` (намеренно исключён, риск записи)
- Проверки бизнес-логики (IDOR, авторизация, workflow), кроме ручного вызова
- Одновременное сканирование нескольких целей
- Повторный запуск, сравнение или экспорт из истории
- Клиентский рендеринг JavaScript
- Веб-панель управления
