**Omega-Fuzz** — локальное терминальное приложение (TUI на [Textual](https://github.com/Textualize/textual) + скриптуемый CLI), которое выполняет обнаружение и тесты безопасности веб-приложений (HTTP-fuzzing) в авторизованных средах: лабораториях, личных зеркалах или явно согласованных тестах.

Инструмент входит в набор `omega-` и построен по принципам Clean Architecture — полные технические подробности см. в `docs/ARCHITECTURE.md`.

## 1. Назначение и область применения

### Что делает Omega-Fuzz

- Обнаруживает периметр одной цели методом BFS с явными ограничениями области (схема, поддомены, разрешённые и запрещённые пути, глубина), никогда без защитных механизмов.
- Выполняет общий fuzzing параметров query string, HTTP-заголовков и найденных на каждом обнаруженном URL форм `GET`, а затем проверяет три семейства сигнатур: не разрушающий отражённый XSS, общую инъекцию (обнаружение ошибки в ответе) и отсутствующие или неправильно настроенные заголовки безопасности — см. [§5](#5-выполняемые-проверки-безопасности).
- Оценивает каждую аномалию по трём осям (влияние, эксплуатируемость, охват) и определяет severity (`low`/`medium`/`high`/`critical`), удаляя дубликаты по `(тип, endpoint, параметр)` и сохраняя лучшее доказательство — см. [§6](#6-оценка-и-severity).
- Поддерживает аутентификацию (cookie, bearer-токен, форма входа) через отдельный YAML-файл; учётные данные никогда не передаются в открытом виде в командной строке.
- Отображает результат в TUI (Textual) или скриптуемом CLI с тремя форматами экспорта (JSON, Markdown, HTML с 5 темами).
- Сохраняет постоянную историю сканирований и их findings в SQLite, а также список повторно используемых избранных целей.
- Требует явного подтверждения (точной фразы в наиболее чувствительных случаях) перед любым агрессивным, расширенным сканированием или сканированием с отключённой проверкой TLS.

### Чего Omega-Fuzz не делает

- Fuzzing JSON-тел — код существует (`plugins/fuzzers/json_body_fuzzer.py`), но не подключён (HTML/BFS-обнаружение не создаёт схемы JSON API и пригодного источника шаблонов).
- Fuzzing форм `POST`/`PUT`/`DELETE` — исключён из автоматического pipeline по соображениям безопасности (риск нежелательной записи на цели); тестируются только формы `GET`.
- Тесты бизнес-логики (IDOR, контроль авторизации, нарушение workflow) — код существует (`plugins/logic_tests/`), но остаётся вне автоматического pipeline; вызывается только отдельно и никогда не запускается стандартным сканированием.
- Параллельное сканирование нескольких целей — одна цель на сканирование.
- Повтор, сравнение или экспорт из экрана История — сохраняются только `Scan` и `Finding` (не полная фактическая конфигурация и не запросы); повтор или повторный экспорт из истории создавал бы данные. Экран это объясняет, а не предлагает функцию молча.
- Рендеринг JavaScript на стороне клиента (страница получается в том виде, в каком отдана сервером, а не выполняется в headless-браузере).
- Веб-панель управления.

## 2. Установка

### Требования

- Python 3.10+
- Интернет-соединение для зависимостей
- Для TUI: шрифт [Nerd Font](https://www.nerdfonts.com/), установленный в терминале, для значка в заголовке — без него символ отображается как пустой квадрат (то же ограничение, что и у эмодзи, но гораздо шире доступное пользователям терминала). Отсутствие шрифта не влияет на работу; это исключительно косметический момент.

### Установка

```bash
[ -d omega-fuzz ] && echo "ℹ️ Уже распаковано здесь, шаг пропущен." || tar -xzf omega-fuzz.tar.gz
cd omega-fuzz/
chmod +x install.sh
./install.sh
```

Скрипт `install.sh`:

1. Создаёт виртуальное окружение `.venv`, если оно ещё не существует.
2. Устанавливает зависимости (`vendor/omega-lib/`, затем `pip install -e .`; `pyproject.toml` остаётся единственным источником истины).
3. Делает `omega-fuzz.sh` и `install.sh` исполняемыми.
4. Добавляет alias `fuzz` в `~/.bashrc` и `~/.zshrc` (без дублирования, если он уже есть).

### Зависимости

Объявлены в `pyproject.toml` (без `requirements.txt`):

- `omega-lib` — общая библиотека набора (темы экспорта, определение терминала, `ConfidenceLevel`) — поставляется в `vendor/omega-lib/`
- `httpx` — асинхронные HTTP-запросы (обнаружение + fuzzing) и потоковая обработка ответа (никогда полный буфер в памяти, даже для файла размером в несколько гигабайт, отдаваемого целью)
- `beautifulsoup4` + `lxml` — извлечение URL и HTML-форм
- `jinja2` — шаблоны HTML-экспорта
- `textual` — TUI-интерфейс, темы, автоматическая адаптация к терминалу
- `pyyaml` — загрузка файла `--auth-config`
- Зависимости разработки (`pip install -e ".[dev]"`): `pytest`, `pytest-asyncio`, `pytest-cov`, `pytest-httpserver`, `ruff`, `mypy`, `import-linter`

## 3. Использование

### Интерактивный режим (TUI)

Рекомендуется для повседневного использования — запускается без аргументов:

```bash
./omega-fuzz.sh
```

если alias создан, просто введите в терминале `fuzz`:

```bash
fuzz
```

Порядок работы: стартовый экран (закрывается по нажатию клавиши или клику) → главное меню (Сканировать / Цели / Настройки / История / Справка) → ввод цели (полный URL, обязательна схема `http://`/`https://`), preset или ручная конфигурация (область + агрессивность), необязательная аутентификация, проверка TLS, переопределения лимитов → экран проверки (простое подтверждение либо точная фраза `OUI-J-AI-L-AUTORISATION` для чувствительных случаев) → сканирование (неопределённый индикатор, кнопка **Остановить** доступна в любой момент) → результаты (findings, экспорт) → история (детали прошедшего сканирования и связанные findings) и избранные цели из главного меню. Адаптация к терминалу (цвета, размер, структурная деградация) выполняется автоматически.

#### Горячие клавиши

| Клавиша | Действие |
|---|---|
| `↑` / `↓` | Навигация между элементами экрана |
| `Tab` / `Shift+Tab` | Навигация между полями формы |
| `Esc` | Возврат к предыдущему экрану (подтверждение выхода на стартовом экране) |
| `t` | Следующая тема (применяется сразу, без подтверждения) |
| `r` | Обновить определение терминала |
| `a` | Показать справку (таблица включённых preset) |
| `q` | Выход (с подтверждением) |
| `Ctrl+P` | Палитра команд (Theme, Выход, Снимок экрана) |

### Языки интерфейса

Интерфейс доступен на 17 языках: французском, английском, испанском, португальском (Бразилия), итальянском, немецком, нидерландском, польском, русском, упрощённом китайском, вьетнамском, тайском, индонезийском, японском, корейском, хинди и арабском. Язык выбирается в Настройках («Язык / Language») и применяется после перезапуска интерфейса; переменная `OMEGA_FUZZ_LANG` (например, `OMEGA_FUZZ_LANG=en ./omega-fuzz.sh`) задаёт язык на время одной сессии. При запуске из omega-suite omega-fuzz использует язык набора. В текстовой консоли Linux (TTY) языки с нелатинской письменностью отображаются на английском в течение сессии. Командная строка остаётся на французском.

### Контакты и поддержка

Справка (клавиша `a`) предлагает экран **Контакты и поддержка**: *Угостить кофе* (страница PayPal разработчика), *Связаться с поддержкой* (адрес электронной почты и контактная форма сайта, показанные открыто), *Зарегистрироваться как пользователь (анонимно)* и *Проверить обновления*. Регистрация добровольная, по умолчанию отключена и отправляется только один раз: она служит лишь для подсчёта пользователей и, по желанию, их континента или страны (закрытые списки, никогда не свободный текст). Отправляются случайно сгенерированный ключ, название программы (`omega-fuzz`) и её версия; никогда имя, имя машины, настройка, цель или результат. IP-адрес не сохраняется в регистрациях, но, как при любом посещении, проходит через проверки безопасности и журнал принимающего сервера. Отозвать регистрацию можно в любой момент на том же экране (*Больше не регистрировать меня*). Проверка обновлений лишь читает список версий, опубликованных на сайте, и никогда без щелчка.

### Скриптовый режим (CLI)

```bash
# Сканировать с готовым preset
./omega-fuzz.sh scan --target https://example.com --preset prod-safe

# Ручная комбинация области и агрессивности (без preset)
./omega-fuzz.sh scan --target https://example.com --scope-profile standard --aggressiveness standard

# С аутентификацией (YAML-файл, никогда открытые данные в командной строке)
./omega-fuzz.sh scan --target https://example.com --preset staging-full --auth-config auth.yaml

# Dry-run: фактическая конфигурация и оценочный план, запросы не отправляются
./omega-fuzz.sh scan --target https://example.com --preset prod-safe --dry-run

# Целевой экспорт (каталог, форматы, тема HTML)
./omega-fuzz.sh scan --target https://example.com --preset prod-safe \
    --output-dir ./rapports --format html --export-theme omega-neon
```

Опции команды `scan`:

| Опция | По умолчанию | Действие |
|---|---|---|
| `--target` | *(обязательно)* | Целевой URL, обязательна схема `http://`/`https://` (никогда не дополняется автоматически) |
| `--preset` | — | Готовый preset (см. [§4](#4-профили-периметра-и-preset)) |
| `--scope-profile` | — | Профиль периметра, в сочетании с `--aggressiveness`, без `--preset` |
| `--aggressiveness` | — | Уровень агрессивности, в сочетании с `--scope-profile`, без `--preset` |
| `--auth-config` | — | YAML-файл аутентификации |
| `--insecure-tls` | выключено | Отключает проверку TLS (вызывает усиленное подтверждение) |
| `--max-duration` | *(из профиля)* | Переопределяет максимальную длительность (секунды) |
| `--max-requests` | *(из профиля)* | Переопределяет максимальное число запросов |
| `--max-tests` | *(из профиля)* | Переопределяет максимальное число тестов |
| `--max-concurrent` | *(из профиля)* | Переопределяет максимальную параллельность |
| `--dry-run` | выключено | Показывает фактическую конфигурацию и оценочный план, не отправляет запросов |
| `--output-dir` | `var/exports/` | Каталог экспортируемых отчётов с именами `<preset>-<метка времени>.<расширение>` (можно переопределить в Настройках) |
| `--format` | `all` | `json`, `markdown`, `html` или `all` |
| `--export-theme` | `omega-base` | Тема экспортируемого HTML-отчёта (не влияет на json/markdown) |

Подкоманды `history`/`show` в CLI нет: история и избранные цели доступны только в TUI.

Если alias создан `install.sh`, команда `fuzz scan ...` работает из любого места терминала, без префикса `./omega-fuzz.sh`.

## 4. Профили периметра и preset

### Профили периметра

| Профиль | Режим | Макс. глубина | Ограничения |
|---|---|---|---|
| `strict` | точная цель | 1 | Блокирует `/health`, `/ready`, `/metrics`, `/favicon.ico`, `/robots.txt` |
| `standard` | + поддомены | 2 | Блокирует обычные статические поддомены, технические пути и ресурсы (изображения/css/js/шрифты) |
| `large` | + поддомены | 4 | Блокирует только технические пути и ресурсы (включая архивы/PDF) |
| `api` | точная цель | 3 | Ограничивает `/api`, `/v1`, `/v2`; блокирует документацию и ресурсы |
| `custom` | + поддомены | 3 | Нет ограничений по умолчанию — основа для ручной конфигурации |

Независимо от выбранного профиля список бинарных/крупных расширений (`.iso`, `.zip`, `.exe`, `.mp4` и т. д.) **всегда** исключается из обхода и fuzzing, даже в режиме `custom` — ссылка на такой файл никогда не запрашивается реальным HTTP-запросом, чтобы каталог загрузок не замедлял сканирование на долгие минуты.

### Уровни агрессивности

`doux` · `standard` · `agressif` · `violent` — каждый уровень имеет собственные базовые лимиты (длительность, запросы, тесты, глубина, параллельность), переопределяемые preset при его наличии.

### Готовые preset

| Preset | Периметр | Агрессивность | Макс. время | Макс. запросы | Макс. тесты | Макс. глубина | Усиленное подтверждение |
|---|---|---|---|---|---|---|---|
| `prod-safe` | strict | doux | 300 с | 1 000 | 500 | 1 | нет |
| `staging-full` | standard | standard | 1 800 с | 20 000 | 10 000 | 2 | нет |
| `lab-deep` | large | agressif | 3 600 с | 100 000 | 50 000 | 4 | нет |
| `lab-extreme` | large | violent | 7 200 с | 500 000 | 250 000 | 5 | **да** |
| `api-hardened` | api | agressif | 1 800 с | 50 000 | 25 000 | 3 | нет |

Сканировать блокируется до подтверждения. **Усиленное** подтверждение (ввод точной фразы `OUI-J-AI-L-AUTORISATION`) требуется, если присутствует хотя бы один из трёх факторов: агрессивность `violent`, preset `lab-extreme` или отключённая проверка TLS (`--insecure-tls`) — при необычной комбинации без одного из этих трёх факторов достаточно простого подтверждения да/нет.

## 5. Выполняемые проверки безопасности

Автоматический pipeline для каждого URL, обнаруженного в области (и для каждой найденной там формы `GET`):

| Проверка | Когда выполняется | Что проверяется |
|---|---|---|
| Общий fuzzing параметров | каждый параметр query string | Поведение цели при граничных или некорректных значениях |
| Fuzzing заголовков | один раз на URL, 4 фиксированных заголовка (`User-Agent`, `Referer`, `X-Forwarded-For`, `Accept-Language`) | Поведение цели при граничных или некорректных значениях в заголовке |
| Fuzzing формы (только `GET`) | каждое поле формы `GET`, найденное в области | Поведение цели при граничных или некорректных значениях в поле формы |
| Отражённый XSS | каждый параметр query string | Нефильтрованное отражение payload в ответе (не разрушающее) |
| Общая инъекция | каждый параметр query string | Обнаружение серверной ошибки в ответе на payload инъекции (без специфического fingerprinting SQL/NoSQL) |
| Заголовки безопасности | один раз на URL | Отсутствующие или неправильно настроенные заголовки безопасности в ответе |

Первые три проверки (общий fuzzing параметров/заголовков/формы) — движок мутаций **без обнаружения**: они никогда не создают `Finding` напрямую; учитываются только встреченные ошибки сервера (5xx) в соответствующем `Test`. Findings создают только сигнатуры (XSS, инъекция, заголовки безопасности).

## 6. Оценка и severity

Каждая обнаруженная аномалия оценивается по трём осям (`impact`, `exploitability`, `scope`, от 1 до 5 каждая) в зависимости от характера наблюдения — сопоставление намеренно **консервативное** (нижняя граница диапазона, никакого человеческого подтверждения на этом автоматическом этапе):

| Сырой балл (сумма 3 осей) | Severity |
|---|---|
| ≥ 13 | `critical` |
| ≥ 10 | `high` |
| ≥ 7 | `medium` |
| < 7 | `low` |

Ручная корректировка (`severity_override`) остаётся возможной, но всегда требует явного обоснования. Эквивалентные findings (тот же тип, endpoint и параметр) дедуплицируются с сохранением лучшего доступного доказательства (уровень уверенности `omega_lib.core.confidence.ConfidenceLevel`, затем сырой балл при равенстве).

## 7. Аутентификация

Отдельный YAML-файл (`--auth-config`), никогда открытые учётные данные в командной строке:

| Режим | Действие |
|---|---|
| `none` | Без аутентификации (по умолчанию) |
| `cookie` | Сессионный cookie передаётся напрямую |
| `bearer_token` | Токен `Authorization: Bearer ...` |
| `login_form` | Аутентификация через форму (URL входа, поля пользователя/пароля) |

## 8. Архитектура

Omega-Fuzz организован по принципу **Clean Architecture** (domain / application / infrastructure / interfaces / ports / core / app / plugins), соответствует шаблону набора `omega-` (см. `omega-check`/`omega-deep`/`omega-fold`) и проверяется `import-linter` при каждом изменении. Полные подробности находятся в **`docs/ARCHITECTURE.md`**.

Очень краткий обзор:

```text
src/omega_fuzz/
├── domain/          Чистая доменная логика (цели/область, запросы, тесты, findings, профили, отчёты...)
├── application/     Сценарии использования (commands/queries) и оркестраторы (обнаружение, сканирование, отчёт, лимиты)
├── ports/           Контракты, ожидаемые приложением (http_client, repositories, exporters...)
├── infrastructure/  Конкретные реализации (httpx, BeautifulSoup, SQLite, экспортёры Jinja2 — Textual здесь НЕ используется)
├── interfaces/      tui/ (Textual) и cli/ (скриптуемый), при строгом функциональном паритете
├── plugins/         Fuzzers и сигнатуры (чистые функции, никогда прямого доступа к сети)
├── app/             Сборка (Container, composition root, жизненный цикл)
└── core/            Общий словарь, ошибки, константы
```

Правила проектирования:

- `plugins/fuzzers/` и `plugins/signatures/`: чистые функции, создающие планы тестов (`Test` + `ScanRequest`), никогда не обращаются к `HttpClient`.
- `infrastructure/network/`: выполняет сетевые операции (`httpx`, потоковая передача с ограничением памяти), никогда не выносит суждений.
- `infrastructure/analyzers/`: читает уже полученный ответ, создаёт структурированные `Observation`, никогда не пересчитывает оценку.
- `interfaces/`: только отображение, без бизнес-логики.

## 9. Экспорт

Отчёты Markdown и HTML создаются на языке, выбранном в Настройках («Язык экспорта», по умолчанию язык интерфейса); JSON остаётся данными и не переводится. Отчёты по умолчанию генерируются в `var/exports/` (путь runtime привязан к каталогу проекта, `$OMEGA_FUZZ_VAR_DIR` для переопределения, также переопределяется на экране Настройки) либо по указанному пути (`--output-dir`). Плоское имя файла, без подкаталога: `<preset>-<метка времени>.<расширение>` (например, `prod-safe-2026-09-01_14-30-22.html`).

### JSON, источник истины

Полная структура отчёта (фактическая конфигурация, статистика, тесты, findings), строго сериализуемая в JSON.

### Markdown, компактный отчёт для человека

Читаемый вне терминала, без ANSI-кодов.

### HTML, автономный веб-отчёт

5 тем на выбор (`--export-theme` в CLI, селектор в TUI): `omega-base`, `omega-burn`, `omega-neon`, `light-basic`, `light-alt`.

## 10. История и избранные цели

Каждое сканирование сохраняется (SQLite, `var/db/omega-fuzz.db`) вместе со своими findings и доступно на экране История в TUI. Сохраняются только `Scan` и `Finding` — не полная фактическая конфигурация и не детальные запросы — поэтому с этого экрана невозможны повтор, сравнение или новый экспорт (экран это объясняет, а не создаёт данные).

Экран **Цели** хранит список избранных (нормализованные URL, `var/targets.json`), повторно используемый для прямого заполнения поля Цель нового сканирования.

## 11. Скриншоты

Команда **Снимок экрана** из палитры (`Ctrl+P`): сохраняет SVG текущего экрана TUI по умолчанию в `var/screenshots/`, с возможностью переопределения на экране Настройки (как и каталог экспорта). В Настройках доступна отдельная очистка.

## 12. Совместимость с терминалами

TUI (Textual) автоматически определяет возможности терминала (эмулятор, размер) и адаптирует структурную таблицу стилей (`complete`/`standard`/`reduced`/`mono`) без ручного флага. CLI всегда остаётся простым текстом, независимо от терминала. Политика общая для всего набора `omega-` (`omega-lib`, `terminal/policies.py`).

### Профиль по обнаруженному эмулятору

| Эмулятор | Начальный профиль |
|---|---|
| Ghostty, Alacritty, WezTerm, Kitty | `complete` |
| Konsole, GNOME Terminal, Terminator, Xfce4 Terminal | `standard` |
| xterm, urxvt, современный SSH | `reduced` |
| Linux TTY, старый SSH | `mono` |
| Неизвестный эмулятор | `reduced` (резерв по умолчанию) |

### Профиль по размеру терминала

| Минимальный размер (столбцы × строки) | Предел профиля |
|---|---|
| 120 × 32 | `complete` |
| 100 × 28 | `standard` |
| 80 × 24 | `reduced` |
| ниже | `mono` |

Итоговый профиль — **наиболее ограниченный из двух** (эмулятор и размер) — обновляется в реальном времени клавишей `r`.

## 13. Тесты

```bash
source .venv/bin/activate
lint-imports        # проверяет Dependency Rule (6 контрактов)
pytest -q           # 344 теста
ruff check src tests
mypy -p omega_fuzz
```

Структура: `tests/unit/` (домен и приложение, без реального I/O), `tests/integration/` (реальная файловая система через `tmp_path`, фиктивный HTTP-сервер `pytest-httpserver`, реальная база SQLite, CLI end-to-end), `tests/tui/` (навигация через `Pilot`, структурные проверки — без самопровозглашённой автоматической визуальной проверки).

## 14. Вне области применения

- Fuzzing JSON-тел (код присутствует, не подключён — нет обнаружения схемы API)
- Fuzzing форм `POST`/`PUT`/`DELETE` (исключён намеренно, риск записи)
- Тесты бизнес-логики (IDOR, авторизация, workflow) вне ручного вызова
- Параллельное сканирование нескольких целей
- Повтор, сравнение или экспорт из истории
- Рендеринг JavaScript на стороне клиента
- Веб-панель
